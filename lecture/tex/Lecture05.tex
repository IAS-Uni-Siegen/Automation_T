              \end{itemize}
        \item \textbf{Medium:}
              \begin{itemize}
                \item Copper (twisted pair, RS-485), fibre optics, radio (WLAN, 5G), sometimes power-line.
                \item Defines attenuation, noise, EMC robustness, maximum distance and speed.
              \end{itemize}

      \end{itemize}
  \end{columns}

\begin{frame}{Analog vs Digital Transmission}
  \begin{columns}
    \column{0.35\textwidth}
      \includegraphics[width=\textwidth]{fig/lec05/comm_an_digi.pdf}% second image
    \column{0.65\textwidth}
      \small
      \begin{itemize}
        \item \textbf{Analog transmission}
              \begin{itemize}
                \item Signal amplitude varies \emph{continuously} with time.
                \item Typical in legacy process control: $4\text{--}20\,\mathrm{mA}$ loops, 0–10 V signals.
                \item Very intuitive but sensitive to noise, offset and long-term drift.
              \end{itemize}
        \item \textbf{Digital transmission}
              \begin{itemize}
                \item Information encoded in discrete levels (usually two: ``0'' and ``1'').
                \item Achieved by \emph{sampling} and \emph{quantisation} of analog values.
                \item Robust against moderate noise, allows error detection, addressing and routing.
              \end{itemize}
        \item Industrial networks today are almost exclusively \textbf{digital}; analog signals are converted at the sensor/actuator interface.
      \end{itemize}
  \end{columns}
\end{frame}
%================================================
\begin{frame}{Transmission Directions: Simplex, Half Duplex, Full Duplex}
    \begin{columns}
    \column{0.4\textwidth}
  \includegraphics[width=\textwidth]{fig/lec05/comm_duplex_types.pdf}% third image
  \column{0.6\textwidth}
  \small
  \begin{itemize}
    \item \textbf{Simplex:} unidirectional, e.g. broadcast radio, sensor with one-way telemetry.
    \item \textbf{Half duplex:} bidirectional but not simultaneous.
          \begin{itemize}
            \item Medium is shared in time (master--slave polls, token passing).
            \item Requires arbitration or master control but saves wiring.
          \end{itemize}
    \item \textbf{Full duplex:} simultaneous bidirectional transfer.
          \begin{itemize}
            \item Implemented by separate physical channels or echo cancellation.
            \item Used in switched Ethernet, fibre links, etc.
          \end{itemize}
    \item Choice depends on topology, cost and required throughput; many fieldbuses use \textbf{half-duplex} to keep transceivers simple and robust.
  \end{itemize}
    \end{columns}
\end{frame}
%================================================
\begin{frame}{Serial vs Parallel Transmission}
    \begin{columns}
    \column{0.35\textwidth}
  \includegraphics[width=0.75\textwidth]{fig/lec05/comm_serial_parallel.pdf}% fourth image
      \column{0.65\textwidth}
  \small
  \begin{itemize}
    \item \textbf{Serial transmission}
          \begin{itemize}
            \item Bits sent sequentially over one pair (or one fibre).
            \item Lower pin count, better EMC, easily galvanically isolated.
            \item Dominant for industrial networks: RS-232, RS-485, CAN, Ethernet, etc.
          \end{itemize}
    \item \textbf{Parallel transmission}
          \begin{itemize}
            \item Multiple bits sent simultaneously on separate conductors.
            \item High raw data rate, but only feasible over short distances.
            \item Susceptible to skew, crosstalk and EMC issues.
          \end{itemize}
    \item Modern fieldbuses and Industrial Ethernet variants are all \textbf{serial} links with advanced encoding and framing.
  \end{itemize}
      \end{columns}
\end{frame}
%================================================
\begin{frame}{Serial Transmission: Synchronous vs Asynchronous}
      \begin{columns}
    \column{0.35\textwidth}
  \includegraphics[width=\textwidth]{fig/lec05/comm_sync_async.pdf}% fifth image
      \column{0.65\textwidth}
  \small
  \begin{itemize}
    \item \textbf{Synchronous serial}
          \begin{itemize}
            \item Continuous bit stream with a shared clock (or embedded clock).
            \item High efficiency: little overhead per data word.
            \item Examples: SPI, synchronous HDLC, physical layers of Ethernet.
          \end{itemize}
    \item \textbf{Asynchronous serial}
          \begin{itemize}
            \item Data sent in frames (characters) separated by idle periods.
            \item Each frame has \emph{start}, \emph{data}, optional \emph{parity}, \emph{stop} bits.
            \item Local clocks are allowed to differ slightly; resynchronisation at every start bit.
            \item Example: UART/RS-232/RS-485, classic Modbus RTU.
          \end{itemize}
    \item Many industrial buses use \textbf{half-duplex, asynchronous, serial, digital transmission} over RS-485 to minimise cost and provide robust EMC behaviour.
  \end{itemize}
        \end{columns}
\end{frame}

\begin{frame}{Industrial Communication Requirements}
  \begin{columns}
    \column{0.45\textwidth}
      \includegraphics[width=\textwidth]{fig/lec05/comm_requirements_levels.pdf}% requirements image
    \column{0.55\textwidth}
      \small
      \begin{itemize}
        \item Plant communication can be grouped into hierarchical levels:
              \begin{itemize}
                \item \textbf{Level 3 -- Company:} ERP, MES, enterprise IT.
                \item \textbf{Level 2 -- Workshop / Cell:} production planning, supervision, SCADA.
                \item \textbf{Level 1 -- Machines:} PLCs, CNC, drive controllers.
                \item \textbf{Level 0 -- Field:} sensors, actuators, I/O modules.
              \end{itemize}
        \item \textbf{Data volume vs reaction time}:
              \begin{itemize}
                \item Upper levels: large data blocks, relaxed timing (seconds–minutes).
                \item Lower levels: small data units (bits, words) with tight deadlines (ms).
              \end{itemize}
        \item No single bus can optimally serve all levels; hence the coexistence of fieldbus and Ethernet-based networks.
      \end{itemize}
  \end{columns}
\end{frame}

        \item \textbf{Fieldbuses / device buses (Level 1):}

        \item \textbf{Local area networks / data buses (Levels 2–3):}
              \begin{itemize}
                \item Based on Ethernet TCP/IP, support large data volumes and standard IT services (FTP, HTTP, OPC UA).
                \item Industrial variants: Profinet, EtherNet/IP, Modbus/TCP, POWERLINK, etc.
              \end{itemize}
      \end{itemize}

\begin{frame}{Industrial Communication: Big Picture}
  \small
  \begin{itemize}
    \item \textbf{Physical / link level:}
          \begin{itemize}
            \item Analog vs digital signalling, serial vs parallel, synchronous vs asynchronous,
                  simplex / half / full duplex.
            \item Implementation on copper, fibre or wireless with strong EMC requirements.
          \end{itemize}
    \item \textbf{Protocol level:}
          \begin{itemize}
            \item Framing, addressing, error detection (CRC), and medium access (master–slave, token, CSMA/CD, TDMA).
            \item Real-time behaviour (cyclic vs acyclic traffic, jitter, determinism).
          \end{itemize}
  \end{itemize}
\end{frame}

\begin{frame}{Industrial Communication: Big Picture}
  \small
  \begin{itemize}
    \item \textbf{System level:}
          \begin{itemize}
            \item Matching network type to plant level:
                  \begin{itemize}
                    \item Sensor buses at Level 0.
                    \item Fieldbuses at Level 1.
                    \item Industrial Ethernet and IT networks at Levels 2–3.
                  \end{itemize}
            \item Typical industrial solution: \textbf{half-duplex, asynchronous, serial digital} communication at field level, bridged to high-speed Industrial Ethernet above.
          \end{itemize}
    \item \textbf{Design goal for the engineer:}
          \begin{itemize}
            \item Select and configure networks so that required reaction times, reliability, diagnostics and life-cycle cost are all satisfied for the given application.
          \end{itemize}
  \end{itemize}

\begin{frame}{Physical Media in Industrial Networks}
  \small
  \begin{itemize}
    \item The \textbf{transmission medium} determines:
          \begin{itemize}
            \item Achievable data rate (bandwidth).
            \item Maximum distance without regeneration.
            \item Immunity to electromagnetic disturbances.
            \item Installation cost and mechanical robustness.
          \end{itemize}
    \item Common media in industrial environments:
          \begin{itemize}
            \item \textbf{Twisted pair copper} – cheapest, easy to install, widely used for fieldbuses.
            \item \textbf{Coaxial cable} – better shielding, good for higher frequencies and noise immunity.
            \item \textbf{Optical fibre} – uses light, immune to EMI, ideal for long distances and harsh areas.
          \end{itemize}
  \end{itemize}
\end{frame}
%------------------------------------------------
\begin{frame}{Electrical Standards for Twisted Pair Links}
  \small
  \begin{itemize}
    \item Industrial protocols are often mapped onto simple \textbf{serial line standards}:
          \begin{description}
            \item[RS--232] Point-to-point, single-ended signalling.
                  \begin{itemize}
                    \item Short distances ($\sim$ 15 m), low speed ($\sim$ 20 kbps typical).
                    \item Historically used for configuration ports, engineering tools.
                  \end{itemize}
            \item[RS--422A] Differential signalling, 4-wire, multi-drop.
                  \begin{itemize}
                    \item Full-duplex communication (separate TX/RX pairs).
                    \item Good noise immunity; up to $\approx 1200$ m at moderate speeds.
                  \end{itemize}
            \item[RS--485] Differential signalling, 2-wire, multi-drop.
                  \begin{itemize}
                    \item Half-duplex, several tens of nodes on one bus.
                    \item Backbone for Modbus RTU and many vendor-specific fieldbuses.
                  \end{itemize}
          \end{description}
    \item Differential standards (RS--422/485) are preferred near motors, drives, and switching power stages.
  \end{itemize}
\end{frame}
%------------------------------------------------
\begin{frame}{Network Topologies in Industrial Systems}
  \small
  \begin{columns}
    \column{0.4\textwidth}
      \includegraphics[width=0.7\textwidth]{fig/lec05/comm_topologies.pdf}
    \column{0.6\textwidth}
      \begin{itemize}
        \item \textbf{Point-to-point}: single link between two devices
              (e.g. PLC--drive link).
        \item \textbf{Bus}: all nodes share a common line
              (classic fieldbus, RS485 trunk with drops).
        \item \textbf{Star}: devices connect to a central switch or hub
              (switched Ethernet).
        \item \textbf{Ring}: nodes form a closed loop; traffic passes via
              intermediate stations (Token Ring, some proprietary safety rings).
        \item \textbf{Tree / hierarchical}: combination of stars/buses,
              follows plant structure (cell, line, area).
        \item \textbf{Grid / mesh}: multiple paths; high availability,
              used in high-end process networks.
      \end{itemize}
  \end{columns}

  \small
  \begin{itemize}
    \item Choice of topology affects redundancy, installation cost, and determinism.
  \end{itemize}
\end{frame}

\begin{frame}{Medium Access Control (MAC) in Industrial Networks}
  \small
  \begin{itemize}
    \item Several stations share the same physical medium $\Rightarrow$ need \textbf{rules} to decide who may transmit.
    \item Main MAC strategies in industrial communication:
          \begin{itemize}
            \item \textbf{Master--Slave (polling)} – one central controller grants access.
            \item \textbf{Token passing} – a logical “token” circulates to grant the right to send.
            \item \textbf{Random access / CSMA} – nodes listen to the medium and compete for access.
          \end{itemize}
    \item Key performance aspects:
          \begin{itemize}
            \item Determinism (worst-case delay known?).
            \item Scalability with number of nodes.
            \item Behaviour under high load and in presence of errors.
          \end{itemize}
  \end{itemize}
\end{frame}
%------------------------------------------------
\begin{frame}{Master--Slave Access (Polling)}
  \small
  \begin{columns}
    \column{0.5\textwidth}
      \includegraphics[width=\textwidth]{fig/lec05/master_slave.pdf}
      \begin{itemize}
          \item Advantages:
              \begin{itemize}
                \item Predictable cycle time, simple implementation in devices.
              \end{itemize}
        \item Drawbacks:
              \begin{itemize}
                \item Single point of failure, master can become a bottleneck.
              \end{itemize}
      \end{itemize}
    \column{0.5\textwidth}
      \begin{itemize}
        \item Implemented at the \textbf{data link layer}.
        \item One node is the \textbf{master}:
              \begin{itemize}
                \item Initiates all exchanges (“polls” the slaves).
                \item Decides the sequence and rate of queries.
              \end{itemize}
        \item Other nodes are \textbf{slaves}:
              \begin{itemize}
                \item Only speak when addressed by the master.
                \item Typical response: process data, diagnostics, or “no data”.
              \end{itemize}
        \item Example: \textbf{Profibus DP}, many proprietary RS485-based buses.

      \end{itemize}
  \end{columns}

\end{frame}
%------------------------------------------------
\begin{frame}{Token Ring Access}
  \small
  \begin{columns}
    \column{0.5\textwidth}
      \includegraphics[width=0.75\textwidth]{fig/lec05/token_ring.pdf}
        \begin{itemize}
              \item Pros:
              \begin{itemize}
                \item Highly deterministic, fair sharing of bandwidth.
              \end{itemize}
        \item Cons:
              \begin{itemize}
                \item Token management overhead, sensitivity to a node or link failure
                      (often mitigated by fault-tolerant ring variants).
              \end{itemize}
        \end{itemize}
    \column{0.5\textwidth}
      \begin{itemize}
        \item Also a link-layer MAC scheme.
        \item Stations form a \textbf{logical ring}; a special frame called
              the \textbf{token} circulates.
        \item A node may transmit only while holding the token, then passes it on.
        \item Access order is strictly defined $\Rightarrow$ bounded access delay.
        \item Industrial example: \textbf{Modbus Plus}, some legacy factory networks.
      \end{itemize}
  \end{columns}
\end{frame}
%------------------------------------------------
\begin{frame}{Random Access and CSMA Principles}
  \small
  \begin{columns}
    \column{0.55\textwidth}
      \includegraphics[width=0.75\textwidth]{fig/lec05/random_access.pdf}
\begin{itemize}
              \item In pure CSMA networks, delay and jitter increase strongly with load
              $\Rightarrow$ non-deterministic.
        \item Still attractive in many industrial Ethernet variants when combined with full-duplex switching and traffic engineering.
      \end{itemize}
    \column{0.45\textwidth}
      \begin{itemize}
        \item \textbf{Carrier Sense Multiple Access (CSMA)}:
              \begin{itemize}
                \item Nodes \emph{listen} to the medium before transmitting.
                \item If the channel is free, they start transmission.
                \item If a collision occurs, a recovery procedure is invoked.
              \end{itemize}
        \item Behaviour is similar to “many people around a table”:
              everyone speaks when it becomes quiet again.
\end{itemize}
  \end{columns}
\end{frame}
%------------------------------------------------
\begin{frame}{CSMA/CD vs CSMA/CA in Practice}
  \small
  \begin{itemize}
    \item \textbf{CSMA/CD – Collision Detection} (classic shared Ethernet)
          \begin{enumerate}
            \item Nodes monitor the line while transmitting.
            \item If a collision is detected, they abort the frame.
            \item Wait a random back-off time (binary exponential back-off).
            \item Retry transmission.
          \end{enumerate}
          \begin{itemize}
            \item Collisions waste bandwidth; acceptable on short, lightly loaded segments.
          \end{itemize}
    \item \textbf{CSMA/CA -- Collision Avoidance} (e.g. CAN bus)
          \begin{enumerate}
            \item Nodes start transmission after sensing idle bus.
            \item If two nodes start simultaneously, arbitration on the identifier
                  ensures that only the higher-priority frame continues.
            \item Lower-priority node detects loss of arbitration and retries later.
          \end{enumerate}
          \begin{itemize}
            \item Collisions are \emph{non-destructive}; high-priority traffic is guaranteed.
          \end{itemize}
    \item Design implication: CSMA/CA-type buses (CAN, CANopen, DeviceNet) are very attractive
          for time-critical control traffic at the device level.
  \end{itemize}
\end{frame}

\begin{frame}{From Physical Layer to Industrial Protocols}
  \small
  \begin{itemize}
    \item Physical and link-layer choices (RS232/422/485, Ethernet, fibre, topology, MAC)
          must support required:
          \begin{itemize}
            \item Cycle time / reaction time.
            \item Distance and environmental robustness.
            \item Scalability (number of nodes, bandwidth).
          \end{itemize}
    \item On top of these, \textbf{industrial protocols} define:
          \begin{itemize}
            \item \textbf{Frame formats} (as for Modbus RTU vs Modbus/TCP).
            \item \textbf{Addressing and diagnostics} (device IDs, status codes).
            \item \textbf{Application semantics} (I/O image, parameters, alarms).
          \end{itemize}
    \item Modern plants typically combine:
          \begin{itemize}
            \item Real-time fieldbuses at Level 0/1.
            \item Industrial Ethernet at Level 1/2.
            \item TCP/IP-based IT networks at Level 2/3.
          \end{itemize}
    \item A solid understanding of media, topologies, and MAC schemes is essential
          to choose the right network for each level.
  \end{itemize}
\end{frame}

\begin{frame}{Application-level communication concepts}
  \small
  \begin{columns}[T,totalwidth=\textwidth]
    %------------- Client–Server -------------
    \begin{column}{0.48\textwidth}
      \textbf{Client–Server model}
      \begin{itemize}
        \item \textbf{Client}: actively issues a service request over the network
              (e.g. ``read holding register 40005'').
        \item \textbf{Server}: provides the requested service and returns the result
              (e.g. sensor value, configuration block, file).
        \item Typical services: read/write variables, download parameters,
              diagnostics, file transfer.
        \item Used for \emph{sporadic}, configuration and diagnostic traffic.
        \item Examples: Modbus (master as client, slave as server), OPC~UA services,
              HTTP/REST APIs in modern controllers.
      \end{itemize}
    \end{column}
    %------------- Producer–Consumer -------------
    \begin{column}{0.48\textwidth}
      \textbf{Producer–Consumer model}
      \begin{itemize}
        \item \textbf{Producer}: one node periodically or on event \emph{publishes}
              a data object (e.g. position set-point, status word).
        \item \textbf{Consumers}: one or many nodes \emph{subscribe} and use the
              same data simultaneously.
        \item Efficient for distributing the same process data to many devices
              (drives, I/O modules, HMIs).
        \item Minimises bus load: one frame, many receivers (hardware filtering).
        \item Examples: CANopen/DeviceNet PDOs, Ethernet POWERLINK,
              PROFINET RT multicast.
      \end{itemize}
    \end{column}
  \end{columns}
\end{frame}

\begin{frame}{Traffic types and the concept of profiles}
  \small
  \textbf{Traffic types in industrial networks}
  \begin{itemize}
    \item \textbf{Cyclic (periodic) data}
          \begin{itemize}
            \item Process values refreshed with fixed cycle time (e.g. every 1\,ms).
            \item Small telegrams, strict jitter and latency requirements.
            \item Used for fast control loops: I/O images, drive set-points and feedback.
          \end{itemize}
    \item \textbf{Acyclic (event- or request-based) data}
          \begin{itemize}
            \item Sent on demand for configuration, parameterisation, diagnostics.
            \item Larger payloads, relaxed real-time requirements.
            \item Must not disturb deterministic cyclic traffic (priority / time slots).
          \end{itemize}
    \item \textbf{Isochronous / time-synchronised traffic (in some Ethernet systems)}
          \begin{itemize}
            \item All nodes share a common time base (sub-\(\mu\)s synchronisation).
            \item Supports motion control with tight phase relationships
                  between multi-axis drives (e.g. PROFINET IRT, EtherCAT DC).
          \end{itemize}
  \end{itemize}

\end{frame}

\begin{frame}{Traffic types and the concept of profiles}
  \small
\textbf{Open systems, interoperability and profiles}
  \begin{itemize}
    \item An \textbf{open system} is built from interoperable and interchangeable
          components from different vendors.
    \item \textbf{Interoperability}: devices understand each other’s communication
          services → strict adherence to protocol specifications.
    \item \textbf{Interchangeability}: one device can be replaced by another
          (possibly from another vendor) without modifying (for example, the PLC program) → adherence to \textbf{application profiles}.
    \item A \textbf{profile} is a standardised description of functions and
          parameters for a device class (e.g. drives, encoders, I/O).
          \begin{itemize}
            \item Defines mandatory / optional objects, semantics, units, scaling.
            \item Typically distributed as electronic description files:
                  EDS, GSD, GSDML, XML, etc.
            \item Examples: PROFIdrive, CiA~402 (drive profile for CANopen/EtherCAT),
                  Encoder profiles, IO-Link device description.
          \end{itemize}
  \end{itemize}
\end{frame}

\begin{frame}{Industrial Communication Protocols -- Overview}
\footnotesize
\begin{itemize}
  \item \textbf{ASi} – Simple sensor/actuator bus; low-cost wiring; deterministic master–slave polling for binary I/O.
  \item \textbf{CANopen} – CAN-based; distributed control and motion; object dictionary and standardized device profiles.
  \item \textbf{DeviceNet} – CAN-based; focus on plug-and-play integration of sensors, actuators, and drives in factory automation.
  \item \textbf{Ethernet TCP/IP Modbus} – Modbus/TCP on standard Ethernet; very common for PLC–HMI and SCADA communication.
  \item \textbf{Profibus-DP} – High-speed cyclic I/O between PLCs and remote I/O/drives; deterministic and widely deployed.
  \item \textbf{FIPIO} – Deterministic fieldbus with producer–consumer model; used in process and factory automation.
  \item \textbf{Interbus} – Ring-oriented remote I/O system; good synchronisation of many distributed modules.
  \item \textbf{Modbus RTU} – Legacy serial master–slave protocol; extremely simple and still popular in drives and instruments.
\end{itemize}

\vspace{0.1cm}
\centering
\scriptsize
\textit{These protocols span from simple sensor buses (ASi, Modbus) to richer fieldbuses and Ethernet-based solutions for higher-level control.}
\end{frame}

\begin{frame}{AS-Interface (ASi) at a Glance}
  \begin{itemize}
    \item \textbf{Purpose:} Low-cost fieldbus for connecting \textbf{discrete sensors and actuators}
          (binary I/O, motor starters, valve islands) at the lowest level of factory automation.
    \item \textbf{Standardisation:} EN~50295, IEC~62026-2; governed by the AS-International Association.
    \item \textbf{Topology:} \emph{Free topology} (line, star, tree, mixed) without termination;
          allows easy retrofits in existing installations.
    \item \textbf{Communication and power on the same 2-wire cable:}
          \begin{itemize}
            \item Yellow, polarised flat cable carries both \textbf{data (\SI{167}{kbps})} and \textbf{30~V DC} supply.
            \item Separate black cable often used for auxiliary power to actuators.
          \end{itemize}
    \item \textbf{Network size / cycle time:}
          \begin{itemize}
            \item ASi~V1: 1 master + 31 standard slaves, cycle time $\approx \SI{5}{ms}$.
            \item ASi~V2: 1 master + 62 A/B slaves, cycle time $\approx \SI{10}{ms}$.
          \end{itemize}
    \item \textbf{Typical position in automation pyramid:}
          between PLC I/O modules and simple field devices, complementing higher-level networks
          such as Profibus, Profinet, EtherNet/IP, etc.
  \end{itemize}

\end{frame}

\begin{frame}{ASi -- Historical Development}
  \begin{itemize}
    \item \textbf{1990:} Two universities and eleven (mainly German) companies form the ASi consortium
          to define a \textbf{low-cost interface} for sensors and actuators.
    \item \textbf{1992:}
          \begin{itemize}
            \item First ASi chips become commercially available.
            \item Creation of the international AS-International Association (headquartered in Germany).
          \end{itemize}
    \item \textbf{1995:} Establishment of national promotional bodies (France, Netherlands, UK, \dots)
          and growing ecosystem of devices and masters.
    \item \textbf{2001:} ASi~V2 specification:
          \begin{itemize}
            \item Up to \textbf{62 A/B slaves} per master.
            \item Extended support for \textbf{analogue I/O} and improved diagnostics.
            \item Introduction of \textbf{“Safety at Work”} concept for safety-related I/O over standard ASi wiring.
          \end{itemize}
    \item Since then: integration into many PLC platforms (Schneider, Siemens, Rockwell, etc.);
          used in conveyors, packaging machines, automotive body shops, intralogistics, and process auxiliaries.
  \end{itemize}

\end{frame}

\begin{frame}{Link Layer: Medium Access and Reliability}
  \begin{itemize}
    \item \textbf{Medium access:} \textbf{Master–Slave} polling at the link layer.
          \begin{itemize}
            \item Only the master initiates frames on the bus.
            \item Each slave is addressed in turn and may respond within a fixed time slot.
            \item Ensures \textbf{deterministic cycle time} for all I/O points.
          \end{itemize}
    \item \textbf{Useful data per transaction:}
          \begin{itemize}
            \item Up to \textbf{4 output bits} in the master request
                  (3 bits for ASi~V2 A/B slaves in certain profiles).
            \item Up to \textbf{4 input bits} in the slave response.
          \end{itemize}
    \item \textbf{Transmission security:} “Numerous checks” at bit and frame level, e.g.
          \begin{itemize}
            \item Start bit delimiter and end bit delimiter.
            \item Use of half-wave pulses for robust decoding.
            \item Minimum pause between bits and frames.
            \item End-of-frame parity and frame length checks.
          \end{itemize}
    \item Combination of short frames, polling, and error detection gives \textbf{high immunity}
          to industrial noise and predictable reaction times in the millisecond range.
  \end{itemize}
\end{frame}

% -------------------------------------------------
\begin{frame}{Application Layer Services and Traffic Types}
  \textbf{Standardised request classes:}
  \begin{enumerate}
    \item \textbf{Network administration:} addressing, identification, parameter setting, device reset.
    \item \textbf{Cyclic I/O exchange (process data):}
          \begin{itemize}
            \item Max.\ 4 output bits (3 for A/B slaves), 4 input bits per slave.
            \item Cycle time: \SI{5}{ms} (31 slaves) to \SI{10}{ms} (62 slaves).
          \end{itemize}
    \item \textbf{Cyclic network monitoring:} read status / diagnostics (I/O errors, slave faults).
    \item \textbf{Parameter data transmission:} write parameter requests for device configuration.
  \end{enumerate}

  \vspace{0.2cm}
  \textbf{Traffic types:}
  \begin{itemize}
    \item \textbf{Cyclical data:}
          \begin{itemize}
            \item Small amount of process data refreshed periodically according to the polling cycle.
            \item Drives the PLC process image (start/stop, sensor states, actuator commands).
          \end{itemize}
    \item \textbf{Acyclic data:}
          \begin{itemize}
            \item Larger or less time-critical information, exchanged on request or on events:
                  configuration, extended diagnostics, identification, firmware information, etc.
            \item Uses reserved time slots or background bandwidth, so it does not disturb cyclic I/O refresh.
          \end{itemize}
  \end{itemize}
\end{frame}

% -------------------------------------------------
\begin{frame}{Profiles and Device Interchangeability}
  \begin{itemize}
    \item \textbf{Goal:} ensure that devices from different manufacturers with the same function
          can be exchanged without engineering changes.
    \item Every ASi slave carries a \textbf{profile} that is \textbf{engraved in silicon} (read-only).
    \item \textbf{ASi V1: 2-digit profile}
          \[
            \text{Profile} = \text{IO}_{\text{code}} . \text{ID}_{\text{code}}
          \]
          \begin{itemize}
            \item $\text{IO}_{\text{code}}$ – number and arrangement of inputs/outputs (0--F).
            \item $\text{ID}_{\text{code}}$ – device type (e.g. standard I/O module, valve island, motor starter).
          \end{itemize}
    \item \textbf{ASi V2: 4-digit profile}
          \[
            \text{Profile} = \text{IO}_{\text{code}} . \text{ID}_{\text{code}} . \text{ID1}_{\text{code}} . \text{ID2}_{\text{code}}
          \]
          \begin{itemize}
            \item $\text{ID1}_{\text{code}}$ – customisation options (e.g. safety, diagnostics level).
            \item $\text{ID2}_{\text{code}}$ – product sub-type (e.g. number of channels, special behaviour).
          \end{itemize}
    \item Profiles are typically delivered as \textbf{electronic description files}
          (EDS, GSD, etc.), which engineering tools import to configure the network offline.
  \end{itemize}
\end{frame}

\begin{frame}{ASi -- Strengths and Limitations}
  \begin{block}{Strengths}
    \begin{itemize}
      \item Very simple, cost-efficient wiring (two-wire flat cable, piercing connectors).
      \item Deterministic master–slave polling with short and predictable cycle times.
      \item Power and communication on the same cable reduce panel I/O wiring.
      \item Mature ecosystem and strong interoperability via well-defined profiles.
      \item Safety extension (“ASi Safety at Work”) reuses the same infrastructure.
    \end{itemize}
  \end{block}
\vspace{-0.25cm}
  \begin{block}{Limitations}
    \begin{itemize}
      \item Limited payload: few bits per slave, mainly suited for discrete I/O.
      \item Moderate data rate (\SI{167}{kbps}); not appropriate for high-bandwidth motion control.
      \item No intrinsic routing or multi-segment networking at protocol level
            (handled via gateways/masters to higher-level buses).
      \item Analogue and complex devices are supported but less efficiently than in Ethernet-based fieldbuses.
    \end{itemize}
  \end{block}
\end{frame}

\begin{frame}{CANopen --- History (Key Milestones)}
\small
\begin{itemize}
  \item \textbf{1980--1983:} \textbf{CAN} conceived (Bosch) to address robust in-vehicle communication; emphasis on reliability and cost-effective ECUs.
  \item \textbf{1983--1987:} High-volume automotive adoption makes CAN controllers/transceivers economically attractive for industrial devices.
  \item \textbf{1991:} \textbf{CiA (CAN in Automation)} founded to promote and standardize industrial CAN-based communication.
  \item \textbf{1993:} \textbf{CAL (CAN Application Layer)} specifications published: defines mechanisms, but not a complete interoperable device behavior model.
  \item \textbf{1995:} CiA releases \textbf{DS-301} communication profile: \textbf{CANopen} is established as a structured application layer + object model.
  \item \textbf{2001:} CiA releases \textbf{DS-304} (CANopen Safety / “CANsafe”) to support safety-related communication on CANopen networks.
\end{itemize}

\vspace{0.5em}
\footnotesize
CAN specifies mainly \emph{Physical + Data Link behavior}; CANopen completes the ecosystem with \emph{object dictionary, services, and profiles} for interoperability.
\end{frame}

\begin{frame}{CANopen --- Physical Layer Essentials}
\small
    \textbf{Medium and signalling}
    \begin{itemize}
      \item Differential signalling on \textbf{shielded twisted pair} (robust EMC behavior).
      \item 2-wire bus (CAN\_H/CAN\_L); 4-wire sometimes used if supplying power separately in device-specific systems.
    \end{itemize}

    \textbf{Topology and termination}
    \begin{itemize}
      \item \textbf{Bus topology} with short stubs; avoid long tap lines.
      \item \textbf{120~$\Omega$ termination} at both physical ends of the bus to prevent reflections.
    \end{itemize}

    \textbf{Distance vs. bitrate (engineering trade-off)}
    \begin{itemize}
      \item Higher bitrate $\Rightarrow$ shorter permissible bus length (signal integrity, propagation delay).
      \item Typical rule-of-thumb: \textbf{25 m @ 1 Mbps}, up to \textbf{1000 m @ 10 kbps} (installation dependent).
    \end{itemize}

    \textbf{Node count (logical)}
    \begin{itemize}
      \item Up to \textbf{128 node IDs} (1 master + 127 slaves in classical addressing).
    \end{itemize}

\end{frame}

%-------------------- Slide: Link layer - arbitration + models (from image) --------------------
\begin{frame}{CANopen --- Link Layer: Arbitration and Communication Models}
\small
\textbf{Medium access: CSMA/CA with nondestructive arbitration}
\begin{itemize}
  \item Any node may start transmission when bus is idle; collisions are resolved by \textbf{bitwise arbitration}.
  \item Arbitration uses \textbf{dominant/recessive} bits; a transmitter that loses arbitration stops immediately.
  \item \textbf{Priority rule:} Lower identifier value $\Rightarrow$ higher priority (wins arbitration).
\end{itemize}

\textbf{Communication models used by CANopen}
\begin{itemize}
  \item \textbf{Producer/Consumer:} one producer, multiple consumers (typical for \textbf{PDOs}).
  \item \textbf{Client/Server:} request/response (typical for \textbf{SDOs} and configuration).
  \item CANopen combines both to separate \emph{real-time process data} from \emph{parameterization/diagnostics}.
\end{itemize}

\footnotesize
Arbitration gives \emph{deterministic priority}, but not deterministic \emph{latency} unless the network is engineered (busload, message set, priorities).
\end{frame}
%.----------------------------------------
\begin{frame}{CANopen --- Link Layer: Payload and Transmission Reliability}
\small

    \textbf{Max. useful payload}
    \begin{itemize}
      \item Classical CAN frame carries up to \textbf{8 bytes} of application data.
      \item Small payload encourages compact cyclic messages (excellent for sensor/actuator process variables).
      \item Larger transfers are handled at the application layer via \textbf{segmentation} (SDO).
    \end{itemize}

    \textbf{Reliability and error handling (why CAN works in harsh environments)}
    \begin{itemize}
      \item Strong error detection: CRC, bit monitoring, bit stuffing checks, frame format checks.
      \item Error confinement: error counters and \textbf{error states} (error-active / error-passive / bus-off).
      \item Faulty nodes are isolated to protect the bus (critical in industrial uptime scenarios).
    \end{itemize}

    \textbf{Practical takeaway}
    \begin{itemize}
      \item Robustness comes from \emph{physical layer design} + \emph{link-layer checks} + \emph{network engineering discipline}.
    \end{itemize}
\end{frame}

\begin{frame}{CANopen --- Application Layer: Services and Object Types}
\small
\textbf{Core idea:} CANopen standardizes a set of services operating on the \textbf{Object Dictionary} (OD),
so devices behave consistently across vendors.

\begin{itemize}
  \item \textbf{Network administration (NMT):} node state control, start-up, reset, supervision (master/slaves).
  \item \textbf{PDO (Process Data Object):} \textbf{real-time, low-volume} process data (producer/consumer).
        \begin{itemize}\footnotesize
          \item Trigger modes: event-driven (change-of-state), cyclic, SYNC-driven, or polled by master.
        \end{itemize}
  \item \textbf{SDO (Service Data Object):} \textbf{parameter data} (often $>$ 8 bytes) via segmentation (client/server).
  \item \textbf{SYNC / TIME:} synchronization and time distribution for coordinated control.
  \item \textbf{EMCY:} emergency messages for fault signalling; supports fast diagnostics.
  \item \textbf{Heartbeat / Node guarding:} node liveness monitoring (supervision).
\end{itemize}

\footnotesize
PDOs are engineered for deterministic cyclic control; SDOs are engineered for commissioning/configuration without real-time guarantees.
\end{frame}
%----------------------------------------
\begin{frame}{CANopen --- Identifier Allocation (Function Code + Node ID)}
\small
    \textbf{Why identifier structure matters}
    \begin{itemize}
      \item CAN arbitration priority depends on the identifier; CANopen therefore structures identifiers systematically.
      \item \textbf{11-bit base format (common):} split into a \textbf{function code} and a \textbf{node ID}.
    \end{itemize}

    \vspace{0.4em}
    \textbf{Operational interpretation}
    \begin{itemize}
      \item \textbf{Function code} selects the message class (PDO/SDO/EMCY/SYNC, etc.).
      \item \textbf{Node ID} addresses the specific device (often set via DIP switch or configuration).
      \item Engineering implication: critical control PDOs can be assigned higher priority via lower COB-IDs.
    \end{itemize}

    \vspace{0.4em}
    \textbf{Examples of message classes (typical)}
    \begin{itemize}\footnotesize
      \item NMT (network control), SYNC, TIME, EMCY
      \item TPDO/RPDO (transmit/receive PDO)
      \item SDO client$\leftrightarrow$server
      \item Heartbeat
    \end{itemize}
  \end{frame}

\begin{frame}{CANopen --- Strengths and Weaknesses (Engineering View)}
\small
\begin{columns}[T,onlytextwidth]

    \begin{itemize}

\footnotesize
CANopen excels in robust, low-level control applications; careful engineering is needed to fully leverage its strengths.

\begin{frame}[t]{Physical layer (Ethernet): topology, distance, speed, node count}
    \small
    \textbf{Topology:} Ethernet supports multiple topologies.
    Historically: shared bus (coax). Today: \textbf{star/tree} via switches is dominant.

    \textbf{Distance and speed trade-off:}
    \begin{itemize}
      \item Copper twisted pair is commonly limited to \textbf{100 m per link} (typical 100/1000BASE-T).
      \item Fibre extends distance (hundreds of meters to \textbf{kilometers}) and improves EMC immunity.
      \item Higher speeds tighten link budgets and require better cabling, connectors, and installation quality.
    \end{itemize}

    \textbf{Node count:}
    \begin{itemize}
      \item In practice, the number of devices is limited by \textbf{switch ports}, \textbf{addressing},
            and (most importantly) \textbf{traffic engineering} (broadcast domains, scanning rates, congestion).
      \item ``Determinism'' is improved by \textbf{segmentation} (VLANs), \textbf{managed switches}, and
            controlling background services.
    \end{itemize}
\end{frame}

\begin{frame}[t]{Transmission media: coax, twisted pair, fibre}
    \small
    \textbf{Why media selection matters in plants:}
    \begin{itemize}
      \item \textbf{EMC/EMI:} drives, inverters, contactors, and long cable runs create harsh environments.
      \item \textbf{Installation:} bending radius, connector robustness, grounding/shield termination.
      \item \textbf{Maintenance:} fault isolation, segment replacement, and standardization of spare parts.
    \end{itemize}

    \textbf{Typical modern practice:}
    \begin{itemize}
      \item \textbf{Shielded twisted pair} for most machine-level Ethernet.
      \item \textbf{Fibre backbones} between cabinets, buildings, or noisy areas.
      \item Coax is mostly legacy (rare in new industrial deployments).
    \end{itemize}

    \textbf{Design tip for Modbus/TCP:}
    Even though Modbus payloads are small, overall performance is often dominated by
    \textbf{polling strategy}, \textbf{scan rate}, and \textbf{switch queuing} rather than raw bitrate.

\end{frame}

\begin{frame}[t]{Transport / network / link layers: CSMA/CD, packets, and reliability}
  \small
    \textbf{Key characteristics of Modbus Ethernet TCP/IP:}
    \begin{itemize}
      \item \textbf{Medium access method: CSMA/CD} (Carrier Sense Multiple Access with Collision Detection).
      \item \textbf{Determinism:} ``resolved using segmentation'' with \textbf{load factor $< 10\%$}.
      \item \textbf{Transmission method:} in \textbf{packets} / IP datagrams, \textbf{64 to 1500 bytes}.
      \item \textbf{Max useful data:} \textbf{1442 bytes per packet (application protocol data unit-APDU)}.
      \item \textbf{Transmission security:}
      \begin{itemize}
        \item \textbf{CRC32} at link layer level
        \item \textbf{Acknowledgement} at TCP link level
        \item \textbf{Response} at application level (UNITE/Modbus)
      \end{itemize}
    \end{itemize}

    \textbf{Industrial interpretation:}
    \begin{itemize}
      \item TCP reliability can increase latency variability under loss/retransmissions.
      \item Modbus/TCP performance is governed by the \textbf{polling schedule}, timeouts, and the background traffic.
      \item Segmentation (VLANs, separate cells/lines, managed switching) is the primary lever for predictability.
    \end{itemize}

\end{frame}

      \item \textbf{FTP:} file transfer (client/server)
      \item \textbf{SNMP:} network management (configuration/monitoring/administration)
      \item \textbf{DNS:} name-to-IP translation
      \item \textbf{BOOTP:} IP address assignment by server
      \item \textbf{TELNET:} terminal interfacing (ASCII)
      \item \textbf{UNITE \& MODBUS:} client/server protocols (UNITE by Telemecanique; Modbus by Modicon)
      \item \textbf{I/O scanning:} periodic I/O update via automatic Modbus requests

    \textbf{control traffic} (scan cycles) from \textbf{engineering/IT traffic} (web/FTP/management),
    using segmentation and policies (QoS, ACLs, managed switching).

\begin{frame}{Engineering implications of the physical layer}

\begin{block}{Why ``distance depends on medium and speed'' is the key sentence}

    \item Data layout separates:
      \begin{itemize}
        \item \textbf{PZD} (\textit{Prozessdaten}): \textbf{process data} for periodic exchange (e.g., control word, setpoints, status, actual values).
        \item \textbf{PKW} channel: parameters/diagnostics (aperiodic, when needed).
      \end{itemize}
    \item The figure explicitly distinguishes:
      \begin{itemize}
        \item \textbf{Periodic exchanges zone} (real-time I/O),
        \item \textbf{Optional aperiodic exchanges zone} (parameters, service).
      \end{itemize}
  \end{itemize}
  \end{block}

  \begin{block}{Field interpretation}
  \begin{itemize}
    \item In drives, keep PZD minimal and stable for control performance.
    \item Use PKW for commissioning, diagnostics, and parameter tuning with controlled timing impact.
  \end{itemize}
  \end{block}
\end{frame}

\begin{frame}{PKW fields and read/write semantics}

  \begin{block}{Terms defined}
  \begin{itemize}
    \item \textbf{PKW} = Parameter--Kennung--Wert (Parameter--Address--Value)
    \item \textbf{PKE} = Parameter--Kennung (parameter address / identifier)
    \item \textbf{PWE} = Parameter--Wert (parameter value corresponding to the address)
    \item \textbf{PZD} = Prozessdaten (process data)
  \end{itemize}
  \end{block}
\vspace{-0.75cm}
  \begin{block}{PKW usage: command/response patterns}
  \begin{itemize}
    \item \textbf{PKE output:}
      \begin{itemize}
        \item Bits 0 to E: address of variable
        \item Bit F: 0 = single read/write; 1 = continuous read/write
      \end{itemize}
    \item \textbf{R/W output codes:} \texttt{16\#0052} = Read; \texttt{16\#0057} = Write
    \item \textbf{R/W/N input codes:} \texttt{16\#0052} Read correct; \texttt{16\#0057} Write correct; \texttt{16\#004E} Read/Write error
    \item \textbf{PWE input:} value / copy / error (\texttt{0} address incorrect, \texttt{1} write refused)
  \end{itemize}
  \end{block}

\end{frame}

\begin{frame}{DP communication profiles: who talks to whom}
  \justifying
  \begin{block}{Three station types defined}
  \begin{itemize}
    \item \textbf{DP master class 1 (DPM1):} programmable controllers such as \textbf{PLCs, PCs}, etc.
    \item \textbf{DP master class 2 (DPM2):} development or diagnostic tool.
    \item \textbf{DP slave:} peripheral device performing \textbf{cyclic exchanges} with its active station.
  \end{itemize}
  \end{block}

  \begin{block}{Why two master classes?}
  \begin{itemize}
    \item DPM1 is the operational master for cyclic control (runtime determinism).
    \item DPM2 is commonly used for commissioning, diagnostics, parameterization, and service.
    \item Separation helps avoid uncontrolled service traffic disrupting the control loop.
  \end{itemize}
  \end{block}

\end{frame}

\begin{frame}{Link Layer: Access Method and Frame Concept}
    \begin{block}{Key points}
      \begin{itemize}
        \item \textbf{Medium access method:} \textcolor{red}{Master/Slaves}
        \item \textbf{Single frame} contains both sensor (input) and actuator (output) data.
        \item Frame managed like a \textbf{shift register} with \textbf{max. 256 words}.
        \item Each slave (station) is a component of the register.
        \item Hybrid frame supports two data classes (max \textcolor{blue}{32 words per device}):
              \begin{itemize}
                \item \textcolor{red}{Cyclic process data} (periodic slave I/O words)
                \item \textcolor{red}{Acyclic parameter data} (fixed memory space)

      \end{itemize}
    \end{block}

    \begin{block}{Why ``shift-register framing'' matters}
      \begin{itemize}
        \item \textbf{Determinism}: the master controls scan order and timing; no collisions.
        \item \textbf{Cycle time scales} with total frame length (words) and bit rate.
        \item \textbf{Practical PLC view}: cyclic data maps into a \emph{process image} (inputs/outputs updated each scan).
      \end{itemize}
    \end{block}

\begin{frame}{MODBUS: History and Core Idea (Application-Layer Protocol)}
  \begin{itemize}
    \item \textbf{Origin (1979):} Created by \textbf{MODICON} to connect PLCs to programming tools.
    \item \textbf{Today:} Widely used for \textbf{master/client} communications with \textbf{slaves/servers}

    \item \textbf{Engineering relevance:}
          \begin{itemize}
            \item Simple request/response model, deterministic polling by the master.
            \item Large installed base in industry $\Rightarrow$ interoperability and maintainability.
          \end{itemize}
  \end{itemize}
\end{frame}

\begin{frame}{Modbus on RS485: Physical Layer Essentials}
  \begin{itemize}
    \item \textbf{Medium:} \alert{Shielded twisted pair} (differential signalling $\Rightarrow$ noise immunity).
    \item \textbf{Topology:} \alert{Bus type} with tap links and \textbf{line terminators}

    \item \textbf{Device count:} \alert{32 devices} (1 master + 31 slaves) per segment
          \begin{itemize}
            \item Repeaters increase segment count and improve loading margin.
          \end{itemize}
    \item \textbf{Practical caution:} half-duplex bus $\Rightarrow$ only \textbf{one talker at a time}
          (master schedules who talks).

% Slide 3: Link layer view – access method, payload idea, integrity elements
%========================================================
\begin{frame}{Modbus Serial Link Layer View: Who Talks When, and How Integrity is Ensured}
  \begin{itemize}
    \item \textbf{Medium access method:} \alert{Master/Slave}
          \begin{itemize}
            \item Master initiates all transactions; slaves respond only when addressed.
            \item This avoids collisions on a shared serial bus.
          \end{itemize}
    \item \textbf{Transmission method:} \alert{Client/Server}
          \begin{itemize}
            \item Client request $\rightarrow$ server executes function $\rightarrow$ server response.
            \item Typical mapping: \textbf{PLC (client)} reads/writes \textbf{device registers (server)}.
          \end{itemize}
    \item \textbf{Max useful data:} \alert{120 PLC words} (implementation-dependent constraint)
          \begin{itemize}
            \item In practice, Modbus PDU limits and device tables often drive smaller limits.
          \end{itemize}
    \item \textbf{Transmission security:}
          \begin{itemize}
            \item \alert{LRC or CRC} for error detection (CRC16 is common in RTU).
            \item \alert{Start/stop delimiters} for framing (ASCII) and \textbf{silent intervals} (RTU).
            \item \alert{Parity bit} (optional) + \textbf{continuous flow} constraints at byte level.
          \end{itemize}
  \end{itemize}


\end{frame}

% Slide 4: Modbus ASCII vs RTU – what changes and why it matters
%========================================================
\begin{frame}{Modbus ASCII vs Modbus RTU: Same Functions, Different Framing/Encoding}
  \begin{itemize}
    \item \textbf{Two serial encodings:}
          \begin{itemize}
            \item \textbf{ASCII mode:} each byte is sent as \alert{two ASCII characters} (hex representation).
            \item \textbf{RTU mode:} bytes are sent as \alert{binary} (compact), with strict timing.
          \end{itemize}
    \item \textbf{Throughput implication:}
          \begin{itemize}
            \item \textbf{RTU is faster} for the same baud rate (less overhead per payload byte).
            \item ASCII is more verbose but human-readable and easier to debug with simple serial tools.
          \end{itemize}
    \item \textbf{Timing robustness:}
          \begin{itemize}
            \item ASCII allows inserting up to \alert{1 second} time interval between two characters
                  without declaring a framing error (useful on slow/variable links).
            \item RTU relies on \textbf{inter-frame silence} to detect boundaries (tight real-time framing).
          \end{itemize}
    \item \textbf{Engineering takeaway:} Choose \textbf{RTU} for performance and industry default;
          choose \textbf{ASCII} when readability / tolerant timing is valuable.
  \end{itemize}

\end{frame}

\begin{frame}{Structure of a Modbus Frame: Fields and Framing Rules (ASCII vs RTU)}
\begin{columns}[T,onlytextwidth]
  \column{0.6\textwidth}
  \begin{itemize}
    \item \textbf{Same structure for request and response.}
    \item \textbf{Core fields (conceptual):}

            \item \textbf{Address:} which slave (unit id) should respond.
            \item \textbf{Function:} operation (read/write registers/coils, diagnostics, etc.).
            \item \textbf{Data:} addresses, counts, values (payload).

  \end{itemize}

      \item \textbf{Common debugging workflow:}
          \begin{enumerate}
            \item Identify frame boundary (silence or :/CRLF).

\begin{frame}{Strengths and Limitations of Modbus (engineering view)}
\justifying

  \begin{block}{Limitations}
\begin{itemize} 
  \item \textbf{Limited data types}: primarily supports simple data types (coils, registers); complex types require custom handling.
  \item \textbf{Scalability constraints}: limited to 247 devices per network segment; performance degrades with many devices.
  \item \textbf{Lack of built-in security}: no native encryption or authentication mechanisms; vulnerable to cyber threats.
  \item \textbf{Basic error handling}: relies on simple checksums; lacks advanced error correction features.
  \item \textbf{No formal timing guarantees}: while master/slave is deterministic, Modbus does not specify timing constraints.
  \item \textbf{Vendor-specific extensions}: variations in implementation can lead to interoperability issues.
\end{itemize}
\end{block}
\end{frame}
