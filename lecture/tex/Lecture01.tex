%% What is Automation? %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{What is Automation?}
  \textbf{Working definition for this course}\\[2mm]
  \emph{Automation is the purposeful application of mechanical, electrical, and computer technologies to reduce human involvement in task performance-without necessarily removing humans from the loop.}\\
  Highly interdisciplinary, it encompasses: combine elements of sensor technology, actuator technology, control technology, communication technology, real-time software, and data science, among other things.
  \vspace{2mm}
  \textbf{Key nuances}
  \begin{itemize}
    \item \textbf{Displace vs. replace:} automation often reallocates human effort to higher-value tasks rather than eliminating it.
    \item \textbf{Hardware and software co-design:} improvement may be purely software (e.g., CAD workflows) or mechatronic (robotic cells).
    \item \textbf{Beyond factories:} retail checkout, medical devices, energy systems, mobility-all are automation domains.
  \end{itemize}
\end{frame}

\begin{frame}{Automation - example case of manufacturing systems}
  \textbf{Automation in manufacturing} can appear in:
  \begin{itemize}
    \item \textbf{Manufacturing support systems} - e.g., Computer aided design (CAD), computer aided manufacturing (CAM), computer-integrated manufacturing (CIM)\footnotemark, and material requirement planning (MRP).
    \item \textbf{Manufacturing systems} - the actual production and material-handling equipment.
  \end{itemize}
  \vspace{3mm}
  \textbf{Focus of this section:}
  Automation that directly reduces the level of human participation in manufacturing processes.\\
  \vspace{3mm}
  \textbf{Three principal types of automation:}
  \begin{enumerate}
    \item Fixed automation
    \item Programmable automation
    \item Flexible automation
  \end{enumerate}
  \footnotetext[2]{\textbf{Computer-integrated manufacturing (CIM)} - links both levels by connecting support systems directly with factory automation for a fully integrated enterprise.}
\end{frame}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%% Fixed Automation %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Fixed Automation}
  \textbf{Definition:}  
  Equipment designed to perform a specific sequence of operations for one product or family of products.\\
  \vspace{2mm}
  \textbf{Key characteristics}
  \begin{itemize}
    \item High \textbf{production rates}, low to high product complexity.
    \item Very limited product variety; reconfiguration requires major setup time.
    \item High initial cost but low unit cost at large volumes.
    \item Typical of flow-line and assembly systems.
  \end{itemize}
  \vspace{3mm}
  \textbf{Examples:}
  \begin{itemize}
    \item Transfer lines for engine blocks.
    \item Automated bottling or packaging lines.
    \item Semiconductor assembly lines.
  \end{itemize}
  \vspace{3mm}
  \textbf{Technology note:}  
  Modern fixed systems may embed PLCs or computer control for limited adaptability, but mechanical configuration remains largely fixed.
\end{frame}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%% Programmable Automation %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Programmable Automation}
  \textbf{Definition:}  
  Automation that allows the operating sequence or equipment configuration to be changed through program modification.
  \vspace{2mm}\\
  \textbf{Key characteristics}
  \begin{itemize}
    \item Handles \textbf{moderate product variety} and \textbf{medium production volumes}.
    \item Reprogramming enables new tasks, but setup/changeover time can be long.
    \item Combines mechanical flexibility with electronic control.
    \item Core element of almost all modern automated systems.
  \end{itemize}
  \vspace{3mm}
  \textbf{Enabling technologies:}
  \begin{itemize}
    \item \textbf{CNC (Computer Numerical Control)} - programmable motion and tool paths.
    \item \textbf{Robotic technology} - reprogrammable manipulators for various tasks.
    \item \textbf{PLC (Programmable Logic Control)} - discrete logic sequencing and interlocks.
  \end{itemize}
  \vspace{3mm}
  \textbf{Used in:} Machining, welding, assembly, and process industries.
\end{frame}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%% Flexible Automation %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Flexible Automation}
  \textbf{Definition:}  
  An extension of programmable automation with \textbf{no lost time for changeover} between products.\\
  \vspace{2mm}
  \textbf{Key characteristics}
  \begin{itemize}
    \item Capable of producing different parts in any order with little or no manual intervention.
    \item Combines features of fixed and programmable automation.
    \item Uses integrated computer control, sensors, and communication networks to recognize and adjust to part variations automatically.
    \item Supports \textbf{high product variety} and \textbf{moderate to high production rates}.
  \end{itemize}
  \vspace{3mm}
  \textbf{Examples:}
  \begin{itemize}
    \item Flexible manufacturing systems (FMS).
    \item CNC machining cells with automatic tool changers and pallet systems.
    \item Robotized assembly lines with vision feedback.
  \end{itemize}
\end{frame}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%% Key Takeaways %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Key Takeaways}
  \begin{itemize}
    \item Automation types differ primarily in \textbf{variety}, \textbf{volume}, and \textbf{changeover capability}.
    \item \textbf{Fixed} $\rightarrow$ highest rate, least flexibility.\\
          \textbf{Programmable} $\rightarrow$ moderate rate, adaptable via reprogramming.\\
          \textbf{Flexible} $\rightarrow$ high variety, minimal setup delay.
    \item Programmable and flexible automation underpin \textbf{modern Industry 4.0} and \textbf{reconfigurable manufacturing}.
    \item Engineers must select the automation type based on economic trade-offs between productivity, product mix, and lifecycle adaptability.
  \end{itemize}
\end{frame}

\begin{frame}{Technical System -- Definition and Structure}
  \textbf{Definition}\\
  A \textbf{technical system} is characterized by its \textbf{inputs}, \textbf{outputs}, \textbf{function}, and \textbf{structure}. It comprises several \textbf{subsystems} arranged hierarchically and interacting with each other.\\
  \vspace{-1.5mm}
  \begin{columns}
    \begin{column}{0.45\textwidth}
      \textbf{Key points}
        \begin{itemize}
          \item Each subsystem has a specific function (mapping of input $\rightarrow$ output).
          \item Abstraction helps describe and model complex installations independent of their concrete hardware.
        \end{itemize}
      \textbf{Reading the diagram}\\
      \footnotesize
      Inputs are processed through subsystems $S_1,\ldots,S_n$ within defined system boundaries to produce outputs. Subsystems can themselves contain elements and control logic.
    \end{column}
    \begin{column}{0.45\textwidth}
      \begin{figure}
        \centering
        \includegraphics[width=\linewidth]{fig/lec01/tech_system.pdf}
        \caption{System and subsystem of a technical system (source: 
        \href{https://doi.org/10.1007/978-3-662-69243-1}{Weyrich, M., 
        \textit{Industrial Automation and Information Technology}, 
        Springer Vieweg, Berlin/Heidelberg, 2024})}		
      \end{figure}
    \end{column}
  \end{columns}
\end{frame}

\begin{frame}{Technical Facility — Concrete Realization}
  \textbf{Definition: }
  A \textbf{technical facility} is a concrete collection of equipment, devices, and machinery that work together to achieve a purpose. It is a physical implementation of one or more technical systems.\\
  \vspace{1.5mm}
  \begin{columns}
    \begin{column}{0.5\textwidth}
      \textbf{Example (process plant excerpt)}
      \begin{itemize}
      \item Raw materials A and B; valves, piping, reactor; sensors and actuators.
      \item \textbf{Control signals} command actuators; \textbf{measurement signals} report states.
      \item Output is a new substance/product C.
      \end{itemize}
    \end{column}

%% Technical Process — Functional Abstraction %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Technical Process — Functional Abstraction}
  \textbf{Definition (DIN IEC 60050-351 / VDI Glossary): }\\
  A \textbf{technical process} is the complete set of interacting operations by which \textbf{matter, energy, or information} is transformed, transported, or stored.
  \begin{columns}[T,onlytextwidth]
    \column{0.5\textwidth}
      \textbf{Why abstract?}
      \begin{itemize}
        \item Real-time information processing and distributed integration require a \textbf{function-oriented} view.
        \item Focus on \textbf{subprocesses}, their interrelations, and \textbf{command/state variables}.
      \end{itemize}
      \vspace{1.5mm}
      \footnotesize
      \textbf{Example sequence}\\[1mm]
      P1: Filling \quad P2: Reaction \quad P3: Discharge\\
      Inputs: inflow A and B \quad Output: product C\\
      Measured/commanded: valve openings, flow rates, temperatures, levels.
    \column{0.5\textwidth}
      \begin{figure}
        \includegraphics[width=\linewidth]{fig/lec01/example_tech_process.pdf}
        \caption{Example of a technical facility (adapted from

        \textit{Industrial Automation and Information Technology:

      \end{figure}
  \end{columns}
\end{frame}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%% Relating the Terms in Practice %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Relating the Terms in Practice}
  \textbf{From concrete to abstract and back}
  \begin{enumerate}
    \item \textbf{Technical system} — abstract structure of subsystems and functions (what maps to what).
    \item \textbf{Technical facility} — physical realization (hardware: valves, pumps, reactors, sensors).
    \item \textbf{Technical process} — functional chain of operations (filling $\rightarrow$ reaction $\rightarrow$ discharge) with \textbf{inputs/outputs} and \textbf{state \& command variables}.
  \end{enumerate}
  \vspace{2mm}
  \textbf{Signal viewpoints}
  \begin{itemize}
    \item \emph{Inputs/Outputs}: material/energy/information entering or leaving the process.
    \item \emph{Command variables}: actuator setpoints (e.g., valve opening).
    \item \emph{State variables}: measured quantities (e.g., flow rate, temperature, level).
  \end{itemize}
  \vspace{2mm}
  \textbf{Takeaway}\\
  Use \emph{system} to reason about structure, \emph{facility} to reason about hardware, and \emph{process} to reason about operations and signals—then connect all three with software and communication to realize automation.
\end{frame}

%% What is an Automaton? %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{What is an \textit{Automaton}?}
  \textbf{Definition(DIN IEC 60050-351 - concise): }\\
  \emph{A self-acting artificial system whose behaviour is governed by given decision rules (discretely or continuously). Its output variables are generated from its input and state variables.}\\
  \vspace{2mm}
  \textbf{Implications}
  \begin{itemize}
    \item Autonomy arises from \textbf{rules/relationships} linking inputs, states, and outputs.
    \item Can operate in discrete-event fashion (sequencing) or continuous-time regulation.
    \item An \textbf{automaton} is the basic building block of automation technology.
  \end{itemize}
  \vspace{1mm}
  \textbf{From devices to systems}
  \begin{itemize}
    \item Modern automation focuses on \textbf{orchestrating subsystems} that cooperate to perform tasks.
    \item Interest shifts from isolated functions to \textbf{how functions are connected}.
  \end{itemize}
\end{frame}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%% Automaton = Technical Process + Automation System + User %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Automaton = Technical Process + Automation System + User}
  \begin{columns}[T,onlytextwidth]
    \column{0.62\textwidth}
      \textbf{Constituent parts}
      \begin{itemize}
        \item \textbf{Technical process}: the physical/chemical/information transformation (process step $n$ and neighbours).
        \item \textbf{Automation system}: sensors, controllers, actuators implementing the decision rules.
        \item \textbf{User (human operator)}: activates/deactivates, monitors, and intervenes in exceptions.
      \end{itemize}
      \textbf{Signal view}
      \begin{itemize}
        \item \emph{Signals from sensors} $\rightarrow$ internal state/measurement.
        \item \emph{Signals to actuators} $\rightarrow$ commands to influence the process.
      \end{itemize}
    \column{0.35\textwidth}
      %\centering
      \begin{figure}
        \includegraphics[width=\linewidth]{fig/lec01/automation_human_user.pdf}\\
        \caption{Technical system with automation and human in the loop (source: 
        \href{https://doi.org/10.1007/978-3-662-69243-1_2}{Weyrich, M., 2024. Industrial Automation and Information Technology. 
        Berlin, Germany: Springer.})}
      \end{figure}
  \end{columns}
  \textbf{Role of the human}\\
  A special \textbf{monitoring} function remains; the user decides \textbf{when/where} to employ the automaton within a defined context.
\end{frame}

%% Degree of Automation and Taylorian Background %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Degree of Automation and Taylorian Background}
  \textbf{Degree of automation (DIN IEC 60050-351)}\\
  \emph{Proportion of automatic functions relative to the entire set of functions of a system or facility.}\\
  \vspace{2mm}
  \textbf{Taylorism and early industrial automation}
  \begin{itemize}
    \item Production decomposed into \textbf{detailed tasks} via labour studies and management.
    \item Enables direct comparison of human vs machine for \textbf{time, quality, and cost}.
    \item Example: \textbf{welding robot} executes a specified seam; quality becomes more reproducible, but setup/programming costs arise.
  \end{itemize}
  \vspace{1mm}
  \textbf{Limits: Taylor's ``vicious circle''}
  \begin{itemize}
    \item Increasingly specialized subprocesses $\Rightarrow$ complex dependencies and inflexibility.
    \item Changing functions requires significant \textbf{engineering effort}.
  \end{itemize}
\end{frame}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%% Towards Flexible Automata %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Towards Flexible Automata}
  \textbf{Raising applicability without full reprogramming}
  \begin{itemize}
    \item Add \textbf{sensing} to compensate disturbances (e.g., thermal distortion during welding).
    \item Use feedback to adapt within the \textbf{dedicated function} while avoiding time-consuming reprogramming.
  \end{itemize}
  \vspace{2mm}
  \textbf{Modern direction}
  \begin{itemize}
    \item Combine \textbf{software} with \textbf{standardized \& modular systems} to increase \textbf{flexibility and applicability}.
    \item Move from isolated automata to \textbf{integrated automated systems} with coordinated functions.
  \end{itemize}
  \vspace{2mm}
  \textbf{Design takeaway}
  \begin{itemize}
    \item Specify the \emph{context of use}, the \emph{degree of automation}, and the \emph{intervention rules} for the human.
    \item Architect sensor-decision-actuation loops that allow \textbf{bounded autonomy} and graceful user override.
  \end{itemize}
\end{frame}

%% Summary for Practice %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Summary for Practice}
  \begin{itemize}
    \item An \textbf{automaton} = automation system + technical process, supervised by a \textbf{user}.
    \item \textbf{Degree of automation} quantifies how much is automatic; it varies by task and context.
    \item Historical Taylorism enabled productivity but also rigidity; modern systems target \textbf{flexibility} through sensing, software, and modularity.
    \item Effective automation design balances \textbf{autonomy} with \textbf{human oversight} and clear exception handling.
  \end{itemize}

      \item \textbf{Controller} — processes measurement data and generates control commands.
      \item \textbf{Actuator} — converts control signals into physical action on the process.
    \end{enumerate}
  \end{itemize}

%% The Feedback Control Loop %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{The Feedback Control Loop}
  \textbf{Operating principle}
  \begin{itemize}
    \item \textbf{Reference signal:} desired setpoint from operator or automation program.
    \item \textbf{Controller:} computes the control signal based on the error (difference between reference and actual output).
    \item \textbf{Actuator:} applies control effort (force, torque, motion, etc.) to the process.
    \item \textbf{Sensor:} measures actual output and feeds it back to the controller.
    \item \textbf{Feedback:} compensates for \textbf{disturbances} to maintain system stability and accuracy.
  \end{itemize}
  \vspace{2mm}
  \textbf{Modern trends}
  \begin{itemize}
    \item Physical proximity of components no longer mandatory—virtualized and networked control is possible via industrial communication.
    \item Data-driven feedback enables adaptive and remote control architectures.
  \end{itemize}
\end{frame}

%% Actuators: Converting Signals into Action %%

\begin{frame}{Actuators: Converting Signals into Action}
  \textbf{Definition:}  
  Actuators transform control signals into mechanical or other physical process variables.
  \vspace{1mm}
  \textbf{Forms of actuation}
  \begin{itemize}
    \item \textbf{Electromechanical:} DC, stepper, and servo motors; often coupled with gears and sensors for precise positioning.
    \item \textbf{Fluid systems:} Pneumatic and hydraulic drives—convert pressure or flow into linear or rotary motion.
    \item \textbf{Thermal or chemical:} Generate heat, flow, or chemical reactions to influence process variables.
  \end{itemize}
  \vspace{2mm}
  \textbf{Key developments}
  \begin{itemize}
    \item Integrated electronics and control software → smart servo drives.
    \item Environmentally friendly pneumatics and efficient hydraulic systems.
    \item Specialized actuators: piezo, magnetostrictive, or shape-memory drives.
  \end{itemize}
\end{frame}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%% Control at the Center of Automation %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Control at the Center of Automation}
  \textbf{Terminology (used precisely in this course)}
  \begin{itemize}
    \item \textbf{Open-loop control:} controller output does \emph{not} use the measured process output.
    \item \textbf{Feedforward control (open-loop with disturbance model):} known/disturbance inputs are measured or estimated and compensated \emph{without} comparing to the output.
    \item \textbf{Closed-loop (feedback) control:} measured output is compared to a reference; the error drives the control action.
  \end{itemize}
  \textbf{Key idea} \\
  Real systems often \emph{combine} feedforward (anticipate known effects) with feedback (reject unknown disturbances) for improved performance.
\end{frame}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%% Feedforward Control with Disturbance Detection %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Feedforward Control with Disturbance Detection}
  \begin{columns}[T,onlytextwidth]
    \column{0.65\textwidth}
      \textbf{Structure and assumptions}
      \begin{itemize}
        \item Relationships between inputs, outputs, and disturbances are known at design time.
        \item Disturbances that are \textbf{detectable/measurable} can be injected into a compensator to pre-empt their effect.
        \item Unknown or non-detectable disturbances still pass to the output.
      \end{itemize}
    \column{0.35\textwidth}
      \centering
      \textbf{Pros/Cons}
      \begin{itemize}
        \item \(\checkmark\) Fast response, no sensor delay in the loop, can avoid unnecessary actuation.
        \item \(\times\) Model dependence; cannot correct modelling errors or unmeasured disturbances.
      \end{itemize}
  \end{columns}
  \begin{figure}
    \includegraphics[width=0.55\linewidth]{fig/lec01/feedforward_control.pdf}\\
    \caption{Feedforward Control with Disturbance Detection}
  \end{figure}
\end{frame}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%% Closed-Loop (Feedback) Control and Practical Example %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Closed-Loop (Feedback) Control and Practical Example}
  \textbf{Closed-loop principle}
  \begin{itemize}
    \item Measure output \(\rightarrow\) compare with reference \(\rightarrow\) control action reduces error.
    \item Rejects unknown disturbances; tolerates modelling errors.
  \end{itemize}
  \textbf{Example: room thermostat}
  \begin{itemize}
    \item \emph{Feedback only:} keeps temperature at setpoint; sudden window opening (disturbance) causes controller to drive heater hard, wasting energy.
    \item \emph{With feedforward sensor logic:} detect rapid temperature drop due to ventilation, \textbf{temporarily disable} heating (open-loop action), then resume feedback control after window closes.
  \end{itemize}
  \textbf{Lesson:} combine \textbf{feedback} (robustness) with \textbf{feedforward} (anticipation) when disturbance pathways are known.
\end{frame}

\begin{frame}{Choosing Between Control Types}
  \begin{table}
    \small

\begin{frame}{What is Mechatronics?}
  \textbf{Origin \& sense of the term}
  \begin{itemize}
    \item “Mecha” (mechanism) + “tronics” (electronics): products integrate electronics/software \emph{intimately} with mechanisms—boundaries blur.
    \item A \textbf{mechatronic system}: a mechanical machine under electronic (incl.\ software) control.
    \item \textbf{Mechatronics (discipline)}: all subject matter needed to \emph{specify and develop} such systems—modelling/simulation of the machine, sensors/actuators, and the control system.
  \end{itemize}
  \textbf{Canonical scope (per text)}
  \begin{itemize}
    \item \textbf{Mechanical systems}: elements, machines, precision mechanics
    \item \textbf{Electronic systems}: micro/power electronics, sensor \& actuator tech
    \item \textbf{Information technology}: systems theory, automation, software engineering, AI
  \end{itemize}
  \textbf{Modern view}: mechatronics is a \emph{holistic} system-design activity, not just “add electronics to mechanics.”
\end{frame}

%% Hierarchy of Safety Requirements %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Hierarchy of Safety Requirements}
  \textbf{Motivation:}
  \begin{itemize}
    \item To develop a \textbf{safety argument} for a \emph{mechatronic system} that integrates both mechanical and electrical/electronic (E/E) subsystems.
    \item Based on the ISO 26262 hierarchy, safety requirements are cascaded through several levels of abstraction.
  \end{itemize}
  \textbf{Safety hierarchy (ISO 26262):}
  \begin{itemize}
    \item \textbf{Safety Goals} — derived from \emph{item definition}.
    \item \textbf{Functional Safety Requirements} — applied to the \emph{preliminary architecture}.
    \item \textbf{Technical Safety Requirements} — mapped to \emph{system design}.
    \item \textbf{Hardware Safety Requirements} — assigned to hardware design.
    \item \textbf{Software Safety Requirements} — assigned to software design.
  \end{itemize}
  \textbf{Challenge:}  
  No universally accepted equivalent hierarchy yet exists for \emph{mechatronic or mechanical} systems — motivating the need for a unified model.
\end{frame}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%% Functional Safety Concept %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Functional Safety Concept}
  \textbf{Definition:}
  \begin{itemize}
    \item Derived from ISO 26262 — ensures that the system maintains a safe state even under foreseeable faults.
    \item In a \textbf{mechatronic context}, this extends beyond E/E components to include mechanical subsystems.
  \end{itemize}
  \textbf{In Mechatronic Systems:}
  \begin{itemize}
    \item The \textbf{Mechatronic Functional Safety Concept} includes both control logic and the physical plant (mechanical system).
    \item Mechanical aspects formerly referred to as \emph{external measures} are now internalized into the concept.
    \item The concept remains independent of detailed E/E and mechanical designs but defines required safe states and control strategies.
  \end{itemize}
  \textbf{Purpose:}  
  Provide a unified architecture that integrates \emph{mechanical and electrical safety assumptions} early in design.
\end{frame}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%% Technical Safety Concept %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Technical Safety Concept}
  \textbf{Definition:}
  \begin{itemize}
    \item Refines functional safety requirements into detailed, implementable \emph{technical requirements}.
    \item Establishes how the safety goals are realized through both E/E and mechanical design decisions.
  \end{itemize}
  \textbf{In Mechatronic Systems:}
  \begin{itemize}
    \item The \textbf{Mechatronic Technical Safety Concept} links the functional concept with physical system implementation.
    \item It includes mappings between:
      \begin{itemize}
        \item Mechanical design parameters
        \item E/E subsystem performance limits
        \item Interfaces at the \textbf{Mechanical-E/E boundary}
      \end{itemize}
    \item These relationships define how both domains interact to achieve required safety integrity.
  \end{itemize}
  \textbf{Purpose:}  
  Ensure traceability from high-level safety goals down to specific mechanical and E/E design choices.
\end{frame}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%% Hardware Safety and Integration %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Hardware Safety and Integration}
  \textbf{Hardware Safety Requirements:}
  \begin{itemize}
    \item Derived from the technical safety concept; specify measurable reliability and fault tolerance targets.
    \item Include quantitative metrics such as fault rates, diagnostic coverage, and safe failure fraction.
  \end{itemize}
  \textbf{Integration challenges in mechatronic systems:}
  \begin{itemize}
    \item Hardware safety applies not only to electronic hardware but also to:
      \begin{itemize}
        \item Electromechanical interfaces (e.g., actuators, sensors, converters)
        \item Mechanical structures critical to safe operation
      \end{itemize}
    \item Co-validation of mechanical and E/E subsystems is essential to verify safe performance.
  \end{itemize}
  \textbf{Takeaway:}  
  Mechatronic safety demands a \textbf{unifying design ontology} linking functional, technical, and hardware domains — ensuring traceability from system goals down to component implementation.
\end{frame}

%% Introduction to HARA for Mechatronic Systems %%

\begin{frame}{Introduction to HARA for Mechatronic Systems}
  \textbf{Purpose of HARA- Hazard Analysis and Risk Assessment:}
  \begin{itemize}
    \item Identify and evaluate potential hazards that can lead to unsafe conditions in a mechatronic system.
    \item Derive safety goals and requirements systematically from system-level behavior.
  \end{itemize}
  \textbf{Applied example: 4CAS (Four Corner Air Suspension System)}
  \begin{itemize}
    \item 4CAS raises or lowers vehicle body using air springs at each wheel.
    \item Sensors measure ride height; ECU adjusts pressure via electromechanical valves.
    \item Typical functions:
      \begin{itemize}
        \item Maintain level body at selected height.
        \item Adjust vehicle height for comfort, aerodynamics, or off-road conditions.
      \end{itemize}
  \end{itemize}
  \textbf{HARA Objective:}
  Link mechanical (pneumatic, structural) and E/E (electronic, software) subsystems within a unified safety argument.
\end{frame}

%% Hazard Identification and Safety Goal Derivation %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Hazard Identification and Safety Goal Derivation}
  \textbf{Conceptual Flow (from the figure and text)}
  \begin{itemize}
    \item Hazards arise from both \textbf{mechanical} (e.g., over-pressure, spring failure) and \textbf{E/E} (e.g., sensor fault, ECU error) domains.
    \item Each operational situation is evaluated to define corresponding \textbf{Hazardous Events}.
    \item Risk levels (severity, exposure, controllability) determine the \textbf{ASIL} (Automotive Safety Integrity Level).
    \item From hazardous events, \textbf{Mechatronic Safety Goals} are derived — spanning mechanics, electronics, and software.
  \end{itemize}
  \textbf{Example (4CAS):}
  \begin{itemize}
    \item \emph{Hazard:} Loss of air pressure in one corner → vehicle tilt → loss of control.
    \item \emph{Safety Goal:} Maintain stable body height and prevent rapid tilt under fault conditions.
  \end{itemize}
  \textbf{Outcome:}
  The HARA provides the foundational safety reasoning upon which functional, technical, and hardware safety concepts are built.
\end{frame}

%% Safety Concepts in Mechatronic Systems %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Safety Concepts in Mechatronic Systems}
  \textbf{Hierarchy of Safety Concepts (ISO 26262-inspired):}
  \begin{enumerate}
    \item \textbf{Functional Safety Concept (Pars 2)} — defines system-level safe behavior and responses.
    \item \textbf{Technical Safety Concept (Pars 3)} — allocates safety requirements to system elements.
    \item \textbf{Hardware/E/E Technical Safety Concept (Pars 4)} — addresses hardware, software, and interface implementation.
  \end{enumerate}
  \textbf{Integration Challenge:}
  \begin{itemize}
    \item Mechanical and E/E systems must be unified under one safety argument.
    \item Functional $\rightarrow$ Technical $\rightarrow$ Hardware flow ensures traceability from hazard to implementation.
  \end{itemize}
  \textbf{4CAS Context Example:}  
  Air suspension must maintain vehicle height even if a sensor or valve fails — this defines the top-level \emph{Functional Safety Goal}.
\end{frame}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
%% Functional Safety Concept [Pars 2] (1) %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Functional Safety Concept [Pars 2] (1)}
  \textbf{Objective:}
  Translate the \emph{Mechatronic Safety Goals} from HARA into concrete \emph{functional behaviors} that guarantee safety.
  \textbf{Key Components:}
  \begin{itemize}
    \item \textbf{Mechatronic System Architecture} = Mechanical + E/E Architecture.
    \item \textbf{Functional Safety Requirements} are assigned to both mechanical and electronic elements.
    \item \textbf{External Measures} still exist for effects outside system scope (e.g., backup mechanical stops).
  \end{itemize}
  \textbf{Example (4CAS):}  
  If an air-pressure sensor fails, the ECU must detect the fault and switch to a safe mode — e.g., lock ride height until service.
\end{frame}

%% Technical Safety Concept [Pars 3] (1) %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Technical Safety Concept [Pars 3] (1)}
  \textbf{Objective:}
  Refine functional requirements into implementable, verifiable \textbf{technical safety requirements}.
  \textbf{Key Aspects:}
  \begin{itemize}
    \item Extends design to explicit \textbf{mechanical elements} (e.g., actuators, springs).
    \item Defines \textbf{interfaces} between E/E and mechanical subsystems.
    \item Allocates safety requirements across:
      \begin{itemize}
        \item \textbf{E/E System Elements:} controllers, sensors, software.
        \item \textbf{Mechanical System Elements:} valves, cylinders, mounts.
      \end{itemize}
  \end{itemize}
  \textbf{Example (4CAS):}  
  Ensure valve response time and ECU actuation timing meet defined limits so that pressure adjustments remain stable under faults.
\end{frame}

%% Hardware / E/E Technical Safety Concept [Pars 4] (1) %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Hardware / E/E Technical Safety Concept [Pars 4] (1)}
  \textbf{Objective:}
  Detail how E/E and software components implement and verify technical safety requirements.
  \textbf{Elements:}
  \begin{itemize}
    \item \textbf{Hardware Software Interface Specification} — defines signal, timing, and fault-reaction behavior.
    \item \textbf{Design Targets:} fault tolerance, diagnostic coverage, random failure rates.
    \item \textbf{Physically Realised System:} Hardware + Embedded Executable + Mechanical Interface.
  \end{itemize}
  \textbf{Example (4CAS):}  
  ECU performs real-time diagnostics of height sensors; if the sensor drifts, the controller uses redundant input or holds last safe pressure.
\end{frame}

%% Relationship Between Concepts %%
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\begin{frame}{Relationship Between Concepts}
  \textbf{Cascading Structure:}
  \begin{enumerate}
    \item \textbf{Functional Safety Concept} defines “\emph{what}” must be safe.
    \item \textbf{Technical Safety Concept} defines “\emph{how}” it will be made safe.
    \item \textbf{Hardware/E/E Concept} defines “\emph{how it is implemented and verified}”.
  \end{enumerate}
  \textbf{4CAS Example Summary:}
  \begin{itemize}
    \item \textbf{Functional:} Keep vehicle level under all driving modes.  
    \item \textbf{Technical:} Ensure consistent pneumatic pressure control, even with sensor or valve degradation.  
    \item \textbf{Hardware:} Verify electrical and mechanical subsystems meet reliability and timing specifications.
  \end{itemize}
  \textbf{Outcome:}
  These layers ensure complete traceability from hazard → goal → design → verification, across both mechanical and electronic domains.
\end{frame}

\begin{frame}{Reproducibility in Automation Systems (2)}
  \vspace{2mm}
  \textbf{Core principles of reproducibility}
  \begin{itemize}
    \item \textbf{Version control:} Git/GitHub or GitLab to track PLC code, Node-RED flows, and Python scripts.
    \item \textbf{Environment definition:} Docker or Conda environments to reproduce runtime dependencies.
    \item \textbf{Documentation:} Markdown, Jupyter Notebooks, and READMEs for configuration and setup.
    \item \textbf{Automated testing:} Simulate logic and signal behaviour to ensure consistent results.
  \end{itemize}
  \vspace{2mm}
  \textbf{Example:}\\
  A student replicates a temperature-control experiment from another group by cloning the GitHub repo and launching an identical OpenPLC + Node-RED + InfluxDB Docker stack.
\end{frame}
